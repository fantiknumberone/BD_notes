# 08. DDL и нормализация

[[Практика/00. Тренировки по темам|← Все тренировки]] · [[Лекции/03. DDL, типы данных и ограничения|Лекция 3]] · [[Лекции/05. ER-модель — сущности и связи|Лекция 5]] · [[Лекции/06. Реляционная модель и реляционная алгебра|Лекция 6]] · [[Лекции/08. Нормализация и физическое хранение|Лекция 8]]

**8 заданий для PostgreSQL** с подсказками, решениями и ожидаемым поведением.

Здесь проектируем допустимые состояния данных. Сначала назови правило и придумай строку, которую БД обязана отвергнуть. Затем выбери NOT NULL, CHECK, UNIQUE или FK. Для нормализации запиши зависимости: совпадение значений в маленькой выборке ещё не доказывает зависимость.

> [!info] Где выполнять
> Открой отдельную учебную базу PostgreSQL по [[Практика/База billing — устройство и запуск|инструкции запуска]]. Код ниже не запускается браузерной песочницей. Самодостаточные примеры создают объекты в схеме training внутри транзакции и завершаются ROLLBACK; запускай каждый пример отдельно целиком. Для чужого ошибочного решения откат при необходимости выполни вручную.

## 01. Положительная сумма

Создай учебную таблицу корректировок: генерируемый PK, обязательная положительная amount, внешний ID операции уникален. Добавь допустимую строку.

> [!tip]- Направление решения
> CHECK и NOT NULL решают разные задачи.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.adjustments (
>  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
>  amount numeric(10,2) NOT NULL CHECK (amount > 0),
>  external_id text UNIQUE
> );
> INSERT INTO training.adjustments (amount,external_id) VALUES (10,'op-1');
> SELECT amount,external_id FROM training.adjustments;
> ROLLBACK;
> ```
>
> **Проверка:** Получена строка 10.00 и op-1. Отдельно проверь, что NULL и неположительная сумма недопустимы.

## 02. Уникальность пары

Разреши не более одного учебного счёта на subscriber\_id и billing\_period. Отдельный PK сам по себе этого не гарантирует.

> [!tip]- Направление решения
> Идентичность строки и единственность бизнес-комбинации различаются.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.invoices (
>  invoice_id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
>  subscriber_id integer NOT NULL,
>  billing_period text NOT NULL,
>  total_amount numeric(10,2) NOT NULL,
>  UNIQUE (subscriber_id,billing_period)
> );
> INSERT INTO training.invoices (subscriber_id,billing_period,total_amount) VALUES (1,'2025-11',300);
> SELECT subscriber_id,billing_period,total_amount FROM training.invoices;
> ROLLBACK;
> ```
>
> **Проверка:** Первая вставка допустима; вторая с той же парой и другим invoice\_id должна нарушить уникальность.

## 03. Обязательная ссылка

Построй две таблицы так, чтобы событие имело существующего владельца и не допускало NULL owner\_id.

> [!tip]- Направление решения
> FK без NOT NULL не задаёт обязательность.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.owners (id integer PRIMARY KEY);
> CREATE TABLE training.events (
>  id integer PRIMARY KEY,
>  owner_id integer NOT NULL REFERENCES training.owners(id)
> );
> INSERT INTO training.owners VALUES (1);
> INSERT INTO training.events VALUES (10,1);
> SELECT e.id,e.owner_id FROM training.events AS e;
> ROLLBACK;
> ```
>
> **Проверка:** Событие 10 связано с владельцем 1. Несуществующий владелец и NULL должны быть отвергнуты.

## 04. Владелец счёта и платежа

Проверь сочетание invoice\_id и subscriber\_id составным FK, сохранив возможность пополнения без счёта.

> [!tip]- Направление решения
> Ссылка проверяет именно комбинацию; NULL в необязательной привязке имеет собственную семантику.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.invoices_owner (
>  invoice_id integer PRIMARY KEY,
>  subscriber_id integer NOT NULL,
>  UNIQUE(invoice_id,subscriber_id)
> );
> CREATE TABLE training.payments_owner (
>  payment_id integer PRIMARY KEY,
>  subscriber_id integer NOT NULL,
>  invoice_id integer,
>  FOREIGN KEY(invoice_id,subscriber_id)
>    REFERENCES training.invoices_owner(invoice_id,subscriber_id)
> );
> INSERT INTO training.invoices_owner VALUES (10,1);
> INSERT INTO training.payments_owner VALUES (1,1,10),(2,2,NULL);
> SELECT * FROM training.payments_owner ORDER BY payment_id;
> ROLLBACK;
> ```
>
> **Проверка:** Обе показанные строки допустимы. Пара invoice\_id=10, subscriber\_id=2 должна быть отвергнута. В полном проекте дополнительно нужен FK самого subscriber\_id.

## 05. Миграция обязательного поля

Добавь initiated\_by к уже заполненной учебной таблице. Для старых фактов неизвестен инициатор: используй unknown, затем задай DEFAULT и NOT NULL.

> [!tip]- Направление решения
> DEFAULT не является автоматическим обновлением всех старых строк.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.changes (id integer PRIMARY KEY);
> INSERT INTO training.changes VALUES (1),(2);
> ALTER TABLE training.changes ADD COLUMN initiated_by text;
> UPDATE training.changes SET initiated_by = 'unknown' WHERE initiated_by IS NULL;
> ALTER TABLE training.changes ALTER COLUMN initiated_by SET DEFAULT 'customer';
> ALTER TABLE training.changes ALTER COLUMN initiated_by SET NOT NULL;
> ALTER TABLE training.changes ADD CHECK (initiated_by IN ('unknown','customer','operator'));
> INSERT INTO training.changes(id) VALUES (3);
> SELECT * FROM training.changes ORDER BY id;
> ROLLBACK;
> ```
>
> **Проверка:** У старых строк unknown, у новой customer. Ни одна строка не имеет NULL.

## 06. Убери транзитивную зависимость

Вместо строки id абонента, имя, ID тарифа и имя тарифа разложи текущие факты на две таблицы и собери результат обратно.

> [!tip]- Направление решения
> Сформулируй зависимость plan\_id → plan\_name.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.plans (plan_id integer PRIMARY KEY, plan_name text NOT NULL);
> CREATE TABLE training.subs (subscriber_id integer PRIMARY KEY, first_name text NOT NULL,
>  plan_id integer REFERENCES training.plans(plan_id));
> INSERT INTO training.plans VALUES (1,'Basic');
> INSERT INTO training.subs VALUES (1,'Анна',1),(2,'Борис',1);
> SELECT s.subscriber_id,s.first_name,p.plan_name
> FROM training.subs AS s LEFT JOIN training.plans AS p ON p.plan_id=s.plan_id
> ORDER BY s.subscriber_id;
> ROLLBACK;
> ```
>
> **Проверка:** Две строки используют одно хранимое название Basic. Переименование тарифа не требует правки обеих абонентских строк.

## 07. Повторное подключение услуги

Спроектируй факт подключения с собственным ID и двумя ролями ссылок. Один абонент вправе подключить услугу повторно после отключения.

> [!tip]- Направление решения
> Не делай пару subscriber\_id/service\_id единственным ключом отдельного подключения.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.people (id integer PRIMARY KEY);
> CREATE TABLE training.services (id integer PRIMARY KEY);
> CREATE TABLE training.subscriptions (
>  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
>  subscriber_id integer NOT NULL REFERENCES training.people(id),
>  service_id integer NOT NULL REFERENCES training.services(id),
>  started_at timestamp NOT NULL,
>  ended_at timestamp,
>  CHECK (ended_at IS NULL OR ended_at >= started_at)
> );
> INSERT INTO training.people VALUES (1);
> INSERT INTO training.services VALUES (1);
> INSERT INTO training.subscriptions(subscriber_id,service_id,started_at,ended_at)
> VALUES (1,1,'2025-01-01','2025-02-01'),(1,1,'2025-03-01',NULL);
> SELECT subscriber_id,service_id,started_at,ended_at FROM training.subscriptions ORDER BY started_at;
> ROLLBACK;
> ```
>
> **Проверка:** Получены два разных подключения одной пары. Проверка интервалов не запрещает пересечение разных строк — это отдельное возможное требование.

## 08. VIEW как интерфейс

Создай представление текущего абонента и тарифа на реальной схеме public и проверь чтение с ограничением.

> [!tip]- Направление решения
> VIEW хранит запрос, а не отдельный снимок строк.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE VIEW training.v_tariffs AS
> SELECT s.subscriber_id,s.phone_number,t.plan_name
> FROM public.subscribers AS s LEFT JOIN public.tariff_plans AS t ON t.plan_id=s.plan_id;
> SELECT * FROM training.v_tariffs ORDER BY subscriber_id LIMIT 3;
> ROLLBACK;
> ```
>
> **Проверка:** Читается не более трёх первых абонентских строк. После ROLLBACK учебное VIEW не остаётся.
