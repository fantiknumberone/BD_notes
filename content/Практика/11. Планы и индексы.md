# 11. Планы и индексы

[[Практика/00. Тренировки по темам|← Все тренировки]] · [[Лекции/08. Нормализация и физическое хранение|Лекция 8]] · [[Лекции/13. Производительность и индексы|Лекция 13]]

**8 заданий для PostgreSQL** с подсказками, решениями и ожидаемым поведением.

Изучай план как объяснение работы запроса. Сравнивай ожидаемые и фактические строки, способ доступа, повторения loops и буферы. На крошечной учебной базе последовательное чтение часто разумно; наличие индекса не обязывает планировщик его использовать.

> [!info] Где выполнять
> Открой отдельную учебную базу PostgreSQL по [[Практика/База billing — устройство и запуск|инструкции запуска]]. Код ниже не запускается браузерной песочницей. Самодостаточные примеры создают объекты в схеме training внутри транзакции и завершаются ROLLBACK; запускай каждый пример отдельно целиком. Для чужого ошибочного решения откат при необходимости выполни вручную.

## 01. План без выполнения

Получи оценочный план поиска абонента по телефону.

> [!tip]- Направление решения
> Не подменяй EXPLAIN на EXPLAIN ANALYZE без понимания различия.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> EXPLAIN SELECT subscriber_id,phone_number FROM public.subscribers WHERE phone_number='+79100000001';
> ```
>
> **Проверка:** План содержит оценочные cost и rows. Конкретный тип сканирования зависит от размера и статистики.

## 02. Измерение чтения

Измерь чтение событий абонента за фиксированный период с BUFFERS.

> [!tip]- Направление решения
> Read не обязательно является физическим обращением к накопителю.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> EXPLAIN (ANALYZE,BUFFERS)
> SELECT record_id,cost FROM public.call_records
> WHERE subscriber_id=1 AND call_date>=TIMESTAMP '2025-11-01'
>  AND call_date<TIMESTAMP '2025-12-01';
> ```
>
> **Проверка:** Появляются actual time, actual rows, loops и буферы. Цифры не должны совпадать с чужим сервером.

## 03. Составной индекс

На учебной копии создай индекс под абонента и период и сравни план в том же транзакционном опыте.

> [!tip]- Направление решения
> Наличие индекса не является приказом планировщику.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE INDEX training_calls_sub_date_v2 ON public.call_records(subscriber_id,call_date);
> ANALYZE public.call_records;
> EXPLAIN SELECT record_id,cost FROM public.call_records
> WHERE subscriber_id=1 AND call_date>=TIMESTAMP '2025-11-01'
>  AND call_date<TIMESTAMP '2025-12-01';
> ROLLBACK;
> ```
>
> **Проверка:** Запрос корректен, но маленький набор не обязан перейти на индексный план. На большом сравни buffers и фактические строки.

## 04. Покрытие результата

Добавь cost как INCLUDE и объясни, почему Index Only Scan всё ещё зависит от видимости.

> [!tip]- Направление решения
> Покрытие полей и карта видимости — разные условия.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE INDEX training_calls_cover_v2 ON public.call_records(subscriber_id,call_date) INCLUDE(cost);
> EXPLAIN SELECT subscriber_id,call_date,cost FROM public.call_records WHERE subscriber_id=1;
> ROLLBACK;
> ```
>
> **Проверка:** Индекс содержит нужные значения. Наличие Heap Fetches и выбор плана оценивают по реальному выполнению.

## 05. Существующие индексы

Найди определения индексов восьми таблиц public перед предложением нового.

> [!tip]- Направление решения
> FK не создаёт индекс на ссылающейся стороне автоматически.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> SELECT tablename,indexname,indexdef FROM pg_indexes WHERE schemaname='public' ORDER BY tablename,indexname;
> ```
>
> **Проверка:** Видны автоматически созданные PK/UNIQUE и явно заданные индексы исходного скрипта.

## 06. Убери преобразование поля времени

Перепиши фильтр ноября так, чтобы границы были по исходному call\_date.

> [!tip]- Направление решения
> Для даты и времени удобен полуоткрытый диапазон.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> SELECT record_id,call_date FROM public.call_records
> WHERE call_date>=TIMESTAMP '2025-11-01 00:00:00'
>  AND call_date<TIMESTAMP '2025-12-01 00:00:00'
> ORDER BY call_date,record_id;
> ```
>
> **Проверка:** Все времена ноября включены без необходимости угадывать последнюю долю секунды месяца.

## 07. Сравни три формы одного результата

Сравни поиск существования платежа через EXISTS, JOIN с DISTINCT и IN. Сначала докажи одинаковый набор ID, затем сравни EXPLAIN.

> [!tip]- Направление решения
> Без DISTINCT сырой JOIN может иметь другую кратность.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> EXPLAIN SELECT s.subscriber_id FROM public.subscribers AS s
> WHERE EXISTS(SELECT 1 FROM public.payments AS p WHERE p.subscriber_id=s.subscriber_id);
> EXPLAIN SELECT DISTINCT s.subscriber_id FROM public.subscribers AS s
> JOIN public.payments AS p ON p.subscriber_id=s.subscriber_id;
> EXPLAIN SELECT s.subscriber_id FROM public.subscribers AS s
> WHERE s.subscriber_id IN (SELECT subscriber_id FROM public.payments);
> ```
>
> **Проверка:** Планы могут оказаться похожими или различаться. Нельзя заранее объявить один синтаксис всегда самым быстрым.

## 08. Обслуживание и его границы

Объясни назначение двух команд и выполни на своей отдельной учебной копии вне явного BEGIN.

> [!tip]- Направление решения
> VACUUM нельзя выполнять внутри обычного явного блока транзакции.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> ANALYZE public.call_records;
> VACUUM (ANALYZE) public.call_records;
> ```
>
> **Проверка:** Статистика обновляется, мёртвые версии обслуживаются по правилам видимости. Уменьшение файла до минимума не обещано.
