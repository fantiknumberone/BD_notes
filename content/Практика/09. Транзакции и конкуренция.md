# 🧩 09. Транзакции и конкуренция

[[Практика/00. Тренировки по темам|← Все тренировки]] · [[Лекции/09. Транзакции, MVCC и изоляция|Лекция 9]] · [[Лекции/10. Функции и процедуры PostgreSQL|Лекция 10]] · [[Лекции/11. Триггеры и планирование задач|Лекция 11]]

**8 заданий для PostgreSQL** с подсказками, решениями и ожидаемым поведением.

Транзакция защищает связанную операцию, но не исправляет любой алгоритм автоматически. Для каждого сценария назови инвариант и точку конкуренции. Большинство примеров выполняются в одной сессии; последнее задание требует двух отдельных подключений.

> [!info] Где выполнять
> Открой отдельную учебную базу PostgreSQL по [[Практика/База billing — устройство и запуск|инструкции запуска]]. Код ниже не запускается браузерной песочницей. Самодостаточные примеры создают объекты в схеме training внутри транзакции и завершаются ROLLBACK; запускай каждый пример отдельно целиком. Для чужого ошибочного решения откат при необходимости выполни вручную.

## 01. Две прибавки внутри БД

В учебных accounts прибавь к первому балансу 20 и 30 относительными обновлениями.

> [!tip]- Направление решения
> Новое значение вычисляется из сохранённого состояния.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.accounts (account_id integer PRIMARY KEY, balance numeric(10,2) NOT NULL CHECK (balance >= 0));
> INSERT INTO training.accounts VALUES (1,100),(2,50);
> UPDATE training.accounts SET balance=balance+20 WHERE account_id=1;
> UPDATE training.accounts SET balance=balance+30 WHERE account_id=1;
> SELECT * FROM training.accounts ORDER BY account_id;
> ROLLBACK;
> ```
>
> **Проверка:** Первый баланс 150, второй 50 до финального учебного отката.

## 02. Условное списание

Попробуй списать 150 при остатке 100, объединив проверку и изменение в одной команде.

> [!tip]- Направление решения
> Не делай отдельно устаревающее чтение перед безусловной записью.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.accounts (account_id integer PRIMARY KEY, balance numeric(10,2) NOT NULL CHECK (balance >= 0));
> INSERT INTO training.accounts VALUES (1,100),(2,50);
> UPDATE training.accounts SET balance=balance-150
> WHERE account_id=1 AND balance>=150 RETURNING account_id,balance;
> SELECT balance FROM training.accounts WHERE account_id=1;
> ROLLBACK;
> ```
>
> **Проверка:** RETURNING пуст, баланс остаётся 100. Отсутствие строки должен обработать вызывающий код.

## 03. Перевод с инвариантом

Переведи 30 между двумя счетами в общей транзакции и проверь сумму остатков.

> [!tip]- Направление решения
> Один смысловой перевод содержит обе записи.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.accounts (account_id integer PRIMARY KEY, balance numeric(10,2) NOT NULL CHECK (balance >= 0));
> INSERT INTO training.accounts VALUES (1,100),(2,50);
> UPDATE training.accounts SET balance=balance-30 WHERE account_id=1;
> UPDATE training.accounts SET balance=balance+30 WHERE account_id=2;
> SELECT * FROM training.accounts ORDER BY account_id;
> SELECT SUM(balance) AS balance_sum FROM training.accounts;
> ROLLBACK;
> ```
>
> **Проверка:** Остатки 70 и 80, общая сумма 150. На произвольных данных нужны также проверки существования и допустимости каждого шага.

## 04. Откат дополнительной части

Сначала прибавь 20, установи SAVEPOINT, затем прибавь ещё 30 и отмени только второй шаг.

> [!tip]- Направление решения
> ROLLBACK TO и общий ROLLBACK имеют разные границы.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.accounts (account_id integer PRIMARY KEY, balance numeric(10,2) NOT NULL CHECK (balance >= 0));
> INSERT INTO training.accounts VALUES (1,100),(2,50);
> UPDATE training.accounts SET balance=balance+20 WHERE account_id=1;
> SAVEPOINT optional_part;
> UPDATE training.accounts SET balance=balance+30 WHERE account_id=1;
> ROLLBACK TO SAVEPOINT optional_part;
> SELECT balance FROM training.accounts WHERE account_id=1;
> ROLLBACK;
> ```
>
> **Проверка:** До полного финального отката баланс 120. SAVEPOINT не фиксирует первую часть отдельно.

## 05. Оптимистическая версия

Два изменения используют ожидаемую version=0. Второе должно заметить, что версия уже изменилась.

> [!tip]- Направление решения
> Ноль изменённых строк — часть контракта, не автоматический успех.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.versioned_accounts (id integer PRIMARY KEY,balance numeric NOT NULL,version integer NOT NULL);
> INSERT INTO training.versioned_accounts VALUES (1,100,0);
> UPDATE training.versioned_accounts SET balance=balance+20,version=version+1
> WHERE id=1 AND version=0 RETURNING balance,version;
> UPDATE training.versioned_accounts SET balance=balance+30,version=version+1
> WHERE id=1 AND version=0 RETURNING balance,version;
> SELECT * FROM training.versioned_accounts;
> ROLLBACK;
> ```
>
> **Проверка:** Первое обновление даёт 120 и версию 1, второе не возвращает строки. В реальном приложении после конфликта пересматривают всё решение.

## 06. Один внешний платёж — один эффект

Примени две доставки внешней операции bank-42 по 50, но увеличь баланс только один раз.

> [!tip]- Направление решения
> Проверка и запись должны выдерживать конкуренцию, а не только последовательные SELECT.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.bank_accounts(id integer PRIMARY KEY,balance numeric NOT NULL);
> CREATE TABLE training.bank_operations(external_id text PRIMARY KEY,amount numeric NOT NULL);
> INSERT INTO training.bank_accounts VALUES(1,100);
> WITH inserted AS (
>  INSERT INTO training.bank_operations VALUES('bank-42',50)
>  ON CONFLICT(external_id) DO NOTHING RETURNING amount
> )
> UPDATE training.bank_accounts SET balance=balance+COALESCE((SELECT SUM(amount) FROM inserted),0) WHERE id=1;
> WITH inserted AS (
>  INSERT INTO training.bank_operations VALUES('bank-42',50)
>  ON CONFLICT(external_id) DO NOTHING RETURNING amount
> )
> UPDATE training.bank_accounts SET balance=balance+COALESCE((SELECT SUM(amount) FROM inserted),0) WHERE id=1;
> SELECT balance FROM training.bank_accounts WHERE id=1;
> SELECT COUNT(*) AS operation_count FROM training.bank_operations;
> ROLLBACK;
> ```
>
> **Проверка:** Баланс 150, в истории одна операция. Учебный пример предполагает одинаковое содержимое повторной доставки; конфликт содержимого с тем же ID нужно проверять отдельно.

## 07. Устойчивый порядок блокировок

Напиши блокирующее чтение двух счетов так, чтобы операции начинали захват в одном порядке ID.

> [!tip]- Направление решения
> Порядок перечисления значений IN сам по себе не обещает порядок строк.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> BEGIN;
> CREATE SCHEMA IF NOT EXISTS training;
> CREATE TABLE training.accounts (account_id integer PRIMARY KEY, balance numeric(10,2) NOT NULL CHECK (balance >= 0));
> INSERT INTO training.accounts VALUES (1,100),(2,50);
> SELECT account_id,balance FROM training.accounts
> WHERE account_id IN (1,2) ORDER BY account_id FOR UPDATE;
> ROLLBACK;
> ```
>
> **Проверка:** Выбраны ID 1 и 2 по возрастанию с блокировкой до конца транзакции. Факт предотвращения конкретного deadlock проверяют опытом в двух сессиях.

## 08. Опыт в двух сессиях

В отдельной учебной базе открой две сессии. A: BEGIN ISOLATION LEVEL REPEATABLE READ и SELECT баланса. B: UPDATE +1 и COMMIT. A: повтори SELECT, затем ROLLBACK. Повтори весь опыт с Read Committed.

> [!tip]- Направление решения
> Не выполняй все строки как один скрипт одной сессии.

> [!example]- Разбор и один из вариантов решения
>
> ```sql
> -- Сессия A, до действий B:
> BEGIN ISOLATION LEVEL REPEATABLE READ;
> SELECT balance FROM subscribers WHERE subscriber_id=1;
> -- После COMMIT в B, в той же A:
> SELECT balance FROM subscribers WHERE subscriber_id=1;
> ROLLBACK;
>
> -- Сессия B выполняет между двумя чтениями A:
> BEGIN;
> UPDATE subscribers SET balance=balance+1 WHERE subscriber_id=1;
> COMMIT;
> ```
>
> **Проверка:** На RR A продолжает видеть прежний снимок; на RC второй SELECT может увидеть зафиксированное прибавление. Изменение B реально сохраняется в учебной копии.
